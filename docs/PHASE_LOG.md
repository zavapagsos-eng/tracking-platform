## Phase 2 — Database + Event Schema

**Repositório**: `tracking-platform/` (npm workspaces, TypeScript strict).

**`packages/schema` — `TrackingEventV1`**
- Envelope universal versionado (`schema_version: "1.0"`) implementado em Zod, com dispatcher `parseTrackingEvent()` preparado para registrar futuras versões (`SCHEMA_REGISTRY`) sem quebrar eventos antigos.
- Todos os campos de `attribution`/`browser`/`commerce`/`consent` são opcionais — nada é inventado quando ausente.
- Regra estrutural aplicada via `superRefine`: eventos financeiros/servidor (`order_created`, `order_paid`, `order_cancelled`, `refund_created`, `transfer_redeemed`) não podem ter `source.origin === "browser"` (reforça "webhook-first purchase" já no schema, não só na lógica de negócio).
- **Testes**: 9/9 passando (`vitest`) — cobrem evento mínimo válido, defaults, dados de atribuição legítimos não fabricados, rejeição de `event_name` desconhecido, rejeição de identidade ausente, rejeição de `schema_version` não suportada, regra webhook-first, e rejeição de coerção de tipo indevida.
- **Lint**: limpo. **Typecheck**: limpo. **Build**: limpo.

**`packages/db` — Postgres + Drizzle ORM**
- 17 tabelas implementadas conforme o ER diagram da seção H do `ARCHITECTURE.md`: `visitors`, `sessions`, `attribution_touches`, `transfers`, `checkouts`, `orders`, `payments`, `refunds`, `events`, `event_registry`, `meta_deliveries`, `identity_links`, `identity_private`, `consent_states`, `webhook_receipts`, `reconciliation_runs`, `audit_logs`.
- Enums tipados: `shop_role`, `event_source`, `link_confidence` (`DETERMINISTIC|PROBABILISTIC|UNKNOWN`), `transfer_status`, `purchase_state` (state machine da seção 22).
- Constraints que materializam regras do spec diretamente no banco: `transfers.token_hash` único (single-use), `event_registry.event_id` PK (idempotência de Purchase), `webhook_receipts (shop_id, webhook_id)` único (idempotência de webhook), `identity_links` aresta única por `(entity_a_type, entity_a_value, entity_b_type, entity_b_value)`.
- `identity_private` fisicamente separada de `events`/`attribution_touches` (data vault, seção 25).
- Migrations geradas via `drizzle-kit generate` (SQL versionado em `packages/db/migrations/`), aplicadas via `db:migrate`.
- **Testes de integração** (Postgres real, banco `tracking_test`, schema resetado a cada run): 6/6 passando — cadeia visitor→session→touch, rejeição de FK inválida, single-use de transfer, idempotência de `event_registry`, idempotência de `webhook_receipts`, unicidade de aresta no identity graph.

## Phase 3 — Tracking Gateway (ingestion API, identity, transfer create/redeem)

**App**: `apps/gateway` (`@tracking/gateway`), Fastify 5 + TypeScript, escuta em `PORT` (padrão 3000).

**Decisão de design registrada** (não estava explícita no `ARCHITECTURE.md`): quem gera `tracking_id`/`session_id`? Definido que o **cliente** (Web Pixel, Fase 4/6) gera esses UUIDs via `crypto.randomUUID()` e os mantém em cookie first-party — o Gateway nunca gera nem infere identidade, apenas persiste de forma idempotente (`upsertVisitorAndSession`) no primeiro evento recebido para cada ID. Isso mantém o Gateway sem estado quanto à geração de identidade e é consistente com a regra de "nunca usar fingerprinting".

**Endpoints implementados:**
- `GET /health` — liveness, sem checar dependências.
- `GET /ready` — readiness, checa conectividade com Postgres (Redis entra na Fase 11 junto com a fila).
- `POST /v1/events` — ingestão de eventos (um ou lote via `{events:[...]}`, até 50 por request). Valida cada evento com `parseTrackingEvent` (schema Fase 2); por evento válido, faz upsert de visitor/session e grava em `events` + `event_registry` (dedup local, idempotente por `event_id`). Resposta sempre `202`, com detalhamento por item (`accepted`/`duplicates`/`rejected`) — o endpoint nunca derruba a requisição do cliente por causa de um item malformado (fail-open comercial, seção 50).
- `POST /v1/transfer/create` — protegido por assinatura HMAC (`X-Gateway-Signature` sobre o corpo bruto da requisição). Gera token opaco de 256 bits, persiste apenas o hash SHA-256, TTL configurável (`TRANSFER_TOKEN_TTL_SECONDS`).
- `GET /r/:token` — redirect server-assisted (seção 10): registra o momento do handoff, monta o cart permalink de Store B (`/cart/{variant}:{qty},...`) a partir do `cart_snapshot` capturado na criação, anexa o token como cart attribute (`attributes[ttid]`), responde `302`. Nunca marca o token como usado — isso só acontece no redeem.
- `POST /v1/transfer/redeem` — também protegido por HMAC. Valida hash, expiração e status; consumo single-use é atômico (UPDATE condicional dentro de transação, fechando a race entre duas tentativas concorrentes do mesmo token — testado). Em sucesso, cria aresta `DETERMINISTIC` em `identity_links` ligando `session_id` de A a `session_id` de B. Tentativa de reuso é detectada e registrada em `audit_logs` como `transfer_replay_detected`, nunca aceita silenciosamente.

**Ajuste de schema decorrente dos testes (Fase 2 revisitada)**: a FK de `transfers.redeemed_session_id` para `sessions.session_id` foi removida (migration `0001`). Motivo encontrado durante os testes de integração: o redeem pode legitimamente chegar antes (ou em paralelo, por ser fire-and-forget) do evento `page_viewed` que cria a sessão de Store B — exigir a FK quebraria o fluxo real. Passou a seguir o mesmo padrão já usado por `identity_links`: referência por valor, não por FK, para entidades que podem ser criadas por chamadas assíncronas independentes.

**Segurança implementada nesta fase**: HMAC-SHA256 com comparação em tempo constante (`timingSafeEqual`) nos endpoints de transfer; helmet (headers de segurança); CORS restrito a allowlist configurável; rate limiting (100 req/min por IP, a ser ajustado por endpoint conforme necessidade real); token opaco nunca armazenado em texto puro (apenas hash); nenhum secret em log (Fastify configurado com `redact` nos headers sensíveis). Autenticação definitiva via Shopify App Proxy fica para a Fase 4/6, quando o tema real existir.

**Testes**: 10/10 passando (Fastify `.inject()` contra Postgres real — `tracking_test`), cobrindo: liveness/readiness, ingestão válida, idempotência de evento duplicado, rejeição de `order_paid` vindo do browser, lote de eventos, rejeição de transfer sem assinatura, fluxo feliz completo (create → redirect → redeem → link no identity graph), rejeição de token inexistente, rejeição de token expirado, e detecção de replay em token já consumido.

**Smoke test adicional (fora do Vitest)**: build de produção (`npm run build`) executado, servidor real subido com `node apps/gateway/dist/index.js`, fluxo completo validado via `curl` ponta a ponta contra Postgres real, com verificação direta no banco do `identity_links` e `transfers.status = 'redeemed'` resultantes.

**Lint / typecheck / build**: limpos nos três pacotes (`schema`, `db`, `gateway`).

**Pendências explícitas para fases futuras**:
- `Dockerfile` do gateway foi criado (`apps/gateway/Dockerfile`, multi-stage, roda como usuário não-root) mas **não foi possível testar o `docker build` neste ambiente** (Docker-in-Docker indisponível no sandbox) — validar em CI/Fase 16.
- Serviço `worker` removido do `docker-compose.yml` até a Fase 11 (ainda não existe `apps/worker`), para não quebrar `docker compose up` no meio das fases.
- Rate limiting hoje é global (100/min/IP); segmentação por endpoint/rota sensível fica para a Fase 15 (revisão de segurança).
- `GET /r/:token` ainda não construiu a URL real de Store B testada contra uma loja de verdade — depende da confirmação empírica da Fase 4/6 sobre o formato exato de cart permalink aceito pelo tema do cliente.

## Phase 4 — Store A Web Pixel + correção de arquitetura (App Proxy)

**Pesquisa direta no código-fonte oficial `@shopify/web-pixels-extension@2.18.0`** (não apenas documentação renderizada — os `.d.ts` do pacote foram inspecionados diretamente, já que a página `shopify.dev/docs/apps/build/marketing-analytics/pixels-overview` retornou 404 no momento da pesquisa). Achados que resolvem pendências da Fase 0/3:

1. **`Cart.attributes` — confirmado, mas condicional**: o próprio tipo oficial documenta `attributes: Attribute[]` no `Cart`, com a nota *"This property is only available if the shop has upgraded to Checkout Extensibility."* Isso resolve o item em aberto da Fase 0 (risco L.5): a leitura do cart attribute com o transfer token **funciona**, mas só em lojas já migradas para Checkout Extensibility — reforça o risco L.2 já documentado. Nenhuma surpresa nova, mas agora é fato verificado, não suposição.
2. **`browser.sendBeacon` está marcado `@deprecated`** no próprio tipo oficial, com instrução explícita para usar `fetch(..., {keepalive: true})` — o Gateway/pixel adotam exatamente isso (`gatewayClient.ts`), não `sendBeacon`.
3. **`customerPrivacy` do `ExtensionApi`** expõe `subscribe('visitorConsentCollected', ...)` com payload `{customerPrivacy: {analyticsProcessingAllowed, marketingAllowed, preferencesProcessingAllowed, saleOfDataAllowed}}` — exatamente os 4 campos já modelados em `consent_states` (Fase 2) e no `TrackingEventV1.consent` (schema). Validação cruzada da arquitetura original.
4. **Lista real de standard events** inclui todos os da seção 11 do spec, mais `product_removed_from_cart`, `collection_viewed`, `search_submitted` — candidatos a adicionar ao enum de eventos em fase futura, não incluídos agora para não expandir escopo sem necessidade confirmada.

**Correção arquitetural importante (revisita a Fase 3)**: o esquema original de `/v1/transfer/create` e `/v1/transfer/redeem` (HMAC de servidor-a-servidor com segredo compartilhado) **não é seguro para ser chamado direto do navegador** — qualquer segredo embutido em código de pixel/tema é visível a quem inspecionar o código-fonte da página (viola a regra da seção 59: nunca colocar segredo Shopify/app no browser). Isso já havia sido sinalizado como provisório nos comentários da Fase 3. Corrigido nesta fase com **Shopify App Proxy**: o navegador chama um caminho same-origin da própria loja (`/apps/tracking/transfer/create`), Shopify assina a requisição no seu edge com o client secret do app instalado, e o Gateway verifica essa assinatura server-side (`lib/appProxy.ts`, algoritmo verificado contra o exemplo oficial de `shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies`: parâmetros ordenados, concatenados sem separador, HMAC-SHA256 hex). Novas rotas `POST /proxy/transfer/create` e `POST /proxy/transfer/redeem` implementam isso; as rotas `/v1/transfer/*` originais permanecem, mas agora documentadas como uso servidor-a-servidor apenas (nunca client-side).

**Entregas desta fase:**
- `apps/gateway`: `lib/appProxy.ts` (verificação de assinatura App Proxy) + `routes/proxy.ts` (endpoints autenticados por App Proxy). Testado contra o vetor de exemplo oficial da documentação Shopify (`extra=1,2`, `logged_in_customer_id`, `path_prefix`, `shop`, `timestamp`) — 5 testes unitários + 3 testes de integração no fluxo completo create→redeem via App Proxy.
- `extensions/web-pixel-store-a`: extensão real de Web Pixel (App Pixel, `runtime_context = "strict"`), com `shopify.extension.toml` seguindo o schema oficial verificado (`[customer_privacy]`, `[settings.fields.*]`). Código dividido em módulos puros testáveis: `identity.ts` (UUID v4 via `crypto.randomUUID()` com fallback `getRandomValues`, cookies first-party `_tp_tid`/`_tp_sid`), `attribution.ts` (captura fbclid/UTMs da URL, `_fbc`/`_fbp` de cookies top-frame via `browser.cookie`, deriva `_fbc` no formato oficial do Meta quando há `fbclid` legítimo mas ainda não existe cookie real — nunca fabrica `_fbp`), `eventMapper.ts` (mapeia os 4 eventos padrão observáveis em Store A — `page_viewed`, `product_viewed`, `product_added_to_cart`, `cart_viewed` — para `TrackingEventV1`, reaproveitando `event.id`/`event.timestamp` do próprio Shopify em vez de gerar novos), `gatewayClient.ts` (`fetch` com `keepalive: true`, fail-open, nunca lança exceção). 31 testes unitários passando com mocks fiéis aos tipos oficiais do `@shopify/web-pixels-extension`.
- `extensions/checkout-bridge-store-a`: módulo separado (não é um Web Pixel — pixels não podem interceptar cliques/redirecionar) para o gatilho real do handoff A→B: lê `/cart.js`, chama `/proxy/transfer/create` via App Proxy, redireciona para `{gateway}/r/{token}`; em qualquer falha ou timeout (1.5s por padrão), cai para uma URL de checkout de fallback — nunca trava a venda. 8 testes cobrindo sucesso, erro HTTP, erro de rede, timeout, e a ausência de qualquer segredo no payload enviado. Inclui um exemplo de snippet Liquid (`snippets/buy-on-store-b.liquid.example`) documentado como ponto de partida, não como algo pronto para instalar — a integração final depende do tema real do comerciante.

**Testes**: 59/59 passando no monorepo (schema 9, db 6, gateway 18, web-pixel-store-a 18, checkout-bridge-store-a 8). Lint e typecheck limpos em todos os pacotes.

**Pendências explícitas para fases futuras:**
- `shopify.extension.toml` usa um `uid` placeholder — será substituído pelo real quando a extensão for de fato escaffoldada dentro de um app Shopify via `shopify app generate extension` (requer Partner account real, fora do escopo "credenciais genéricas por enquanto").

## Phase 5-6 — Cross-domain bridge (redeem no lado B) + Web Pixel de Store B

**Refactor prévio**: extraído `packages/pixel-kit` (`identity.ts`, `attribution.ts`, `gatewayClient.ts` — antes duplicados dentro de `web-pixel-store-a`) para ser compartilhado entre os pixels de Store A e Store B, já que a lógica de cookie/identidade/atribuição/envio ao Gateway é idêntica nos dois lados; só o `eventMapper.ts` (eventos observados) difere por loja. 19 testes desses módulos migraram junto, sem alterar comportamento (confirmado: mesma contagem de testes, todos passando após a mudança).

Ou seja: mesmo que a loja de Store B não tenha migrado para Checkout Extensibility, o atributo `ttid` (colocado no cart permalink pelo redirect `/r/:token` da Fase 3) sobrevive até o checkout e fica acessível em `event.data.checkout.attributes` no evento `checkout_started`. **Entregas:**

## Phase 7 — Shopify webhooks (orders/paid, refunds, GDPR mandatórios)

**Pesquisa (shopify.dev, confirmada antes de implementar):**
- HMAC de webhook Admin: header `X-Shopify-Hmac-Sha256` = `base64(HMAC-SHA256(rawBody, client_secret))`, comparação em tempo constante. Crítico: o HMAC é calculado sobre os bytes crus exatos do corpo — por isso `verifyShopifyWebhookHmac()` recebe `request.rawBody` (capturado pelo `rawBodyPlugin` já existente da Fase 3), nunca `JSON.stringify(request.body)` re-serializado.
- Headers de entrega: `X-Shopify-Webhook-Id` (idempotência), `X-Shopify-Topic`, `X-Shopify-Shop-Domain`.
- Webhooks GDPR mandatórios (`customers/data_request`, `customers/redact`, `shop/redact`) são obrigatórios para qualquer app Shopify que processa dados de cliente, prazo de resposta de 30 dias, `shop/redact` dispara 48h após desinstalação — confirmado no shopify.dev.
- **Questão em aberto, não resolvida por suposição**: encontrei relatos conflitantes sobre depreciação de `checkout_token`/`cart_token` no payload REST do Order. O changelog oficial só confirma um novo campo `cartToken` no GraphQL (API 2026-07), sem confirmar depreciação do campo REST equivalente. Decisão tomada: o schema aceita os dois campos (`checkout_token` preferido, `cart_token` como fallback) e trata a correlação com `checkouts` como best-effort — nunca bloqueia a ingestão do pedido. Fica **documentado como risco aberto**, a revalidar contra a API version real da loja do comerciante antes de finalizar a Fase 9 (Reconciliation).
- **Decisão fixada** (resolve a pendência registrada em `docs/ARCHITECTURE.md` linha 183, "a fixar na Fase 7"): `orders/paid` é o gatilho autoritativo de "pedido pago" — não `orders/create` + checagem de `financial_status`. Motivo: `orders/paid` dispara sempre que `financial_status` transiciona para `paid`/`partially_paid`, inclusive para pedidos já pagos no momento da criação (Shopify dispara os dois tópicos nesse caso, então não há perda de sinal). Pedidos com captura manual/parcelada continuam fora de escopo — exigem tratamento explícito que ainda não existe, sinalizado no código (`routes/webhooks.ts`) em vez de assumido como resolvido.

**Entregas:**
- `lib/shopifyWebhookAuth.ts`: `verifyShopifyWebhookHmac()`.
- `lib/webhookReceipt.ts`: `recordWebhookReceipt()` — ledger de idempotência `(shop_id, webhook_id)` único, primeira entrega vence, reentregas são reconhecidas e curto-circuitadas antes de qualquer lógica de negócio.
- `lib/orderIngestion.ts`: schemas Zod defensivos para os payloads de Order/Refund (valores monetários mantidos como string ponta-a-ponta, nunca convertidos para float, até a coluna `numeric` do Postgres); `ingestOrderWebhook()`/`ingestRefundWebhook()`; `event_id` determinístico (`{event_name}:{shop_id}:{order_id}` / `refund_created:{shop_id}:{refund_id}`) para que reentregas do Shopify e futuros retries de fila (Fase 11) nunca gerem um segundo evento. Eventos originados de webhook usam um placeholder de identidade "não resolvida" (UUID nulo bem-conhecido) em vez de inventar um `tracking_id`/`session_id` — a Fase 9 (Reconciliation) é quem resolve isso de verdade via `checkout_token`.
- `routes/webhooks.ts`: `POST /webhooks/:store/orders/create|paid|cancelled`, `POST /webhooks/:store/refunds/create`, e os 3 webhooks GDPR mandatórios — todos por loja (`store-a`/`store-b`, cada uma com seu próprio segredo `SHOPIFY_A_WEBHOOK_SECRET`/`SHOPIFY_B_WEBHOOK_SECRET`, nunca compartilhado). Ordem de verificação: loja conhecida → segredo configurado → HMAC válido → idempotência → processamento. Uma requisição com HMAC inválido **não** é gravada no ledger de idempotência — decisão deliberada: como a chave é `(shop_id, webhook_id)` e esse header vem do cliente, gravar tentativas não autenticadas abriria uma forma de um `webhook_id` real (capturado/repetido) ocupar a vaga antes da entrega genuína do Shopify chegar, derrubando-a como "duplicata". Payload malformado (mas HMAC válido) retorna 400 em vez de 500 — Shopify reenviará.
- GDPR: os 3 tópicos são reconhecidos (200) e uma entrada é gravada em `audit_logs` com o `customer.id`/`shop_domain` — **nunca** o email/telefone que o Shopify envia no payload de `customers/data_request`/`customers/redact` (testado explicitamente: o log não deve conter a string do email). **Limite de escopo documentado, não escondido**: esta fase reconhece e audita a entrega, mas não executa a exportação/apagamento de fato — isso depende do Identity Graph (Fase 8) para resolver `customer.id` → `tracking_id` e de uma rotina de purge no data vault, que ainda não existem. Fica como pendência explícita abaixo, não fingido como resolvido.

**Bug real encontrado pelos testes de integração (mesma classe do bug da Fase 3)**: `orders.checkout_token` tinha FK para `checkouts.checkout_token`. ## Phase 8 — Identity Graph

**Lacuna real encontrada antes de poder implementar esta fase**: nenhuma linha jamais foi escrita em `attribution_touches` nem em `checkouts` — as Fases 3-7 persistiam `visitors`/`sessions`/`events`, mas o "touch" de atribuição (UTM/fbclid/fbc/fbp por sessão) e a correlação `session_id <-> checkout_token` nunca foram implementados, embora as tabelas já existissem desde a Fase 2. Sem isso, não havia nada para o grafo de identidade reconstruir — a reconstrução de jornada exige que esses dados já estejam sendo capturados. Corrigido como pré-requisito desta fase (não adiado, porque a Fase 8 depende diretamente disso), documentado abaixo como parte da entrega.

**Decisões de design:**
- **Um touch por sessão, não por evento**: `recordAttributionTouch()` só roda no primeiro evento de cada `session_id` (ver `isNewSession` abaixo), não em todo evento — assim uma visita de 5 páginas gera 1 touch, não 5, batendo com o exemplo do próprio spec (Meta dia 1 / Direto dia 3 / Meta dia 5 → Purchase).
- **`isNewSession` sem condição de corrida**: `upsertVisitorAndSession()` trocou `ON CONFLICT DO UPDATE` por `ON CONFLICT DO NOTHING ... RETURNING` no insert da sessão — a lista de retorno não-vazia é o sinal inequívoco de "esta chamada criou a sessão", em vez de inferir isso de `event_name === "page_viewed"` (que erraria para sessões que começam com outro evento). Quando não é nova, um `UPDATE` separado ainda atualiza `last_event_at`.
- **Classificação de canal (`deriveChannel`) não inventa "pago"**: `fbclid` (o click id do próprio Meta) é o único critério para `is_paid = true` — um `utm_source=meta` sozinho, sem `fbclid`, não é tratado como pago (poderia ser um post orgânico só marcado para tracking). Documentado extensivamente no código porque é uma decisão de classificação, não uma regra do spec escrita literalmente.
- **`fbc`/`fbp` também viram arestas no grafo** (`identity_links`, tipo `fbc`/`fbp` ↔ `session_id`, DETERMINISTIC), como a Seção E do `ARCHITECTURE.md` especifica — permite busca reversa por valor de cookie sem varrer `attribution_touches`.
- **`checkouts` é escrito pelo Web Pixel de Store B, nunca reconstruído a partir do webhook**: só o Pixel sabe qual `session_id` iniciou aquele `checkout_token`; o webhook (Fase 7) só carrega o token em si. Se o Pixel nunca disparar (ad blocker, JS desabilitado, consentimento negado), essa linha genuinamente não existe — tratado como estado esperado (`checkout_not_tracked`), nunca inventado.
- **Traversal do grafo é BFS genérico, não um hop fixo**: hoje só a aresta `session_id <-> session_id` encadeia uma jornada (a ponte cross-domain), então na prática sempre termina em 1 hop — mas a função não assume isso; ela para quando não descobre mais nenhum `tracking_id` novo, então continua correta se um tipo de aresta futuro (ex.: um PROBABILISTIC eventual, sempre auditável) encadear mais de um salto.
- **Toda quebra de cadeia tem um status nomeado explícito** (`order_not_found`, `no_checkout_correlation`, `checkout_not_tracked`, `session_not_tracked`, `ok`) em vez de uma jornada parcial silenciosa — cada uma corresponde a um cenário real e esperado, nunca escondido atrás de uma suposição.

**Entregas:**
- `lib/attribution.ts`: `deriveChannel()` + `recordAttributionTouch()`.
- `lib/checkoutTracking.ts`: `recordCheckoutStart()`.
- `lib/identity.ts`: `upsertVisitorAndSession()` agora retorna `{ isNewSession }`.
- `routes/events.ts`: passa a chamar as duas funções acima no ponto certo do fluxo de ingestão — falhas nelas são logadas mas nunca rejeitam o evento principal (fail-open, spec seção 50).
- `lib/journey.ts`: `findLinksForEntity()` (lookup bidirecional de arestas), `reconstructJourneyByTrackingId()` (BFS pelo grafo + merge cronológico de touches de todos os `tracking_id` alcançados) e `reconstructJourneyByOrderId()` (resolve `order_id -> checkout_token -> session_id -> tracking_id` e delega para a anterior) — esta é a consulta de reconstrução de jornada que o critério de conclusão da Fase 8 pede.

**Bug real pego pelos próprios testes desta fase**: a primeira versão de `reconstructJourneyByTrackingId` reportava a mesma aresta `identity_links` duas vezes (uma para cada lado do BFS, já que a busca por aresta é bidirecional). Corrigido rastreando `link_id` já visitado, para que cada aresta apareça exatamente uma vez em `linkedIdentities` independente de qual lado foi alcançado primeiro.

**Testes**: 30 novos (5 em `lib/attribution.test.ts`, unitários sobre `deriveChannel`; 11 em `lib/journey.test.ts`, integração contra Postgres real cobrindo `isNewSession`, touches, arestas fbc/fbp, `checkouts`, os 4 status de quebra de `reconstructJourneyByOrderId` e a reconstrução completa cross-domain; 2 novos em `server.test.ts`, ponta-a-ponta via HTTP em `/v1/events`, confirmando 1 touch por sessão e a escrita de `checkouts` a partir de um evento real). Total no monorepo: **100/100 passando** (schema 9, db 6, pixel-kit 13, gateway 48, web-pixel-store-a 5, web-pixel-store-b 11, checkout-bridge-store-a 8). Lint, typecheck e build limpos em todos os pacotes.

**Pendências explícitas para fases futuras:**

## Phase 10 — Meta CAPI Service + normalização

**Pesquisa (developers.facebook.com, confirmada antes de implementar):**
- Endpoint verificado: `POST https://graph.facebook.com/{API_VERSION}/{PIXEL_OR_DATASET_ID}/events?access_token={TOKEN}`, corpo `{ data: [event], test_event_code? }`. `access_token` só na URL, nunca no corpo. `event_time` é Unix **segundos**, não milissegundos.
- Regras de normalização/hash de `customer-information-parameters` verificadas campo a campo: `em`/`ph`/`fn`/`ln`/`ct`/`st`/`zp`/`country`/`external_id` são SHA-256 hex, com normalização específica por campo antes do hash (email: trim + minúsculo; telefone: só dígitos; nomes: minúsculo sem pontuação **mantendo** espaços; cidade: minúsculo sem pontuação **e** sem espaços; CEP dos EUA: truncado para os 5 primeiros caracteres; estado/país: minúsculo). `client_ip_address`, `client_user_agent`, `fbc`, `fbp` **nunca** são hasheados — passthrough puro. Um campo que normaliza para vazio é **omitido**, nunca hasheado como string vazia (SHA-256("") é um valor fixo conhecido — hasheá-lo seria fabricar um sinal que não existe).
- **Ambiguidade de terminologia encontrada, documentada em vez de resolvida por suposição**: a documentação atual do Meta chama o identificador do endpoint `/events` de "dataset id" ("server events are linked to a dataset ID and processed like Pixel events"), enquanto o próprio Events Manager ainda rotula o mesmo ID numérico como "Pixel ID" em muitas telas. Não há confirmação de que sejam conceitos diferentes — parece ser uma migração de nomenclatura em andamento sobre o mesmo identificador. Por isso `config.ts` aceita as duas variáveis (`META_PIXEL_ID`, `META_DATASET_ID`); fica marcado para verificação com credenciais reais quando a conta Meta for conectada.
- Versões do Graph API pesquisadas (WebSearch): v26.0 é a mais recente; v20.0 expira em 24/09/2026 (iminente); v18.0/v19.0 já expiradas. Escolhido **v23.0** (válida até 10/2027) como default configurável — não a mais nova, mas a mais segura dentro da janela de validade confortável, evitando obrigar reconfiguração às pressas assim que uma conta real for conectada.

**Decisões de design:**
- **`consent_states` também não tinha nenhum escritor** (mesma classe de lacuna encontrada em `attribution_touches`/`checkouts` na Fase 8) — corrigido como pré-requisito desta fase: `lib/consent.ts` (`recordConsentIfPresent()`, append-only — nunca sobrescreve um registro anterior, preserva histórico; `getCurrentMarketingConsent()`), ligado em `routes/events.ts` incondicionalmente a cada evento (não só em sessão nova, já que consentimento pode mudar a qualquer momento).
- **Regra de fail-closed do gate de consentimento**: ausência de qualquer registro de consentimento ("unknown") é tratada exatamente como "denied" para efeito de liberar um envio ao Meta — é a regra explícita da Seção I do `ARCHITECTURE.md` ("sem consentimento de marketing, evento é registrado internamente mas não expedido ao Meta"), não uma interpretação mais restritiva inventada agora.
- **Dois namespaces de `event_id` distintos, de propósito**: `purchase:{shop_id}:{order_id}` (Meta CAPI, Seção F) é diferente de `order_paid:{shop_id}:{order_id}` (arquivo interno de eventos da Fase 7) — "Purchase" é o nome de evento padrão do Meta, não faz parte do enum interno `TRACKING_EVENT_NAMES`, então em vez de forçá-lo nesse enum só para reaproveitar `recordEvent()`, criei um caminho mais estreito (`ensureEventRegistryRow()`/`markEventMetaSent()` em `lib/eventRegistry.ts`) que escreve só no ledger de dedup, sem arquivo bruto em `events` (não existe payload `TrackingEventV1` correspondente para arquivar).
- **`sendPurchaseToMeta()` aplica dois gates, nesta ordem, antes de qualquer chamada HTTP**: (1) dedup local — nunca reenviar algo já `meta_sent = true`, independente da janela de 48h do próprio Meta; (2) consentimento de marketing. Cada gate rejeitando é um resultado tipado e registrado, nunca um descarte silencioso.
- **`meta_deliveries` grava uma linha por tentativa de envio** (sucesso ou falha), com `http_status`/`response_redacted`/`delivery_status` — histórico de auditoria completo. Um contador de retry/backoff de verdade, através de múltiplas tentativas, fica para a Fase 11 (fila).
- **Backfill de identidade do cliente a partir do Order** (fecha a pendência registrada na Fase 8: "`order_id ↔ email_hash/phone_hash` depende das funções de normalização/hashing do Meta CAPI, Fase 10"): `orderWebhookPayloadSchema` ganhou `email`/`phone`/`customer`/`billing_address` (nomes de campo confirmados contra a doc oficial do recurso Order do shopify.dev). `backfillCustomerIdentityFromOrder()` roda dentro de `ingestOrderWebhook()` — o único lugar que já vê o email/telefone bruto do cliente — resolve o `checkout_token` até a sessão/tracking_id rastreados pelo Pixel, hasheia imediatamente (nunca persiste PII crua em nenhuma tabela), grava em `identity_private` e cria as arestas `order_id ↔ email_hash`/`phone_hash` (DETERMINISTIC) em `identity_links`.
- **Update de `identity_private` nunca regride um hash já existente**: o `set` do `onConflictDoUpdate` é montado só com os campos efetivamente presentes nesta entrega — uma redelivery do `orders/paid` sem escopo de Protected Customer Data (Shopify manda `null` nesse caso) não apaga um hash de email/telefone já capturado por uma entrega anterior.
- **Limite de escopo explícito, documentado no código e na Seção D do `ARCHITECTURE.md`**: o `user_data` do Purchase não inclui `fn`/`ln`/`ct`/`st`/`zp`/`country` ainda — o Order webhook do Shopify carrega nome/endereço de cobrança, mas persistir isso com segurança exige a mesma criptografia em repouso para a qual as colunas `identity_private.first_name_enc`/`last_name_enc`/`address_enc` já foram desenhadas (Seção I) — decisão de infraestrutura de segurança para a Fase 15, não improvisada agora. EMQ portanto não está 100% maximizado ainda; tratado como pendência explícita, não como completo.

## Phase 11 — Fila + retries + DLQ

**Pesquisa (não presumida — feita lendo o próprio pacote instalado, não só a documentação pública, porque a documentação pública se mostrou incompleta/desatualizada em pontos-chave):**
- `bullmq@6.3.4` é a versão atual (`npm view bullmq versions`). Descoberta relevante: a v6 tornou `ioredis` uma **peer dependency opcional** (junto com `pg` e `redis` — a v6 aparentemente também suporta um backend Postgres nativo, algo não documentado nas páginas públicas consultadas). Como `docs/ARCHITECTURE.md` seção B.10/J especifica explicitamente "BullMQ/Redis", este projeto usa o backend Redis (o único especificado), não o backend Postgres — `ioredis` foi adicionado como dependência direta do Gateway.
- A documentação pública (`docs.bullmq.io`) não confirma se BullMQ aceita uma URL de conexão Redis como string diretamente — há uma issue aberta no próprio repositório pedindo esse suporte. Em vez de assumir, o código-fonte instalado (`node_modules/bullmq/dist/esm/classes/redis-connection.js`) foi lido diretamente: `RedisOptions.url` é honrado (`new IORedis(url, rest)` internamente), então `{ url: REDIS_URL, maxRetriesPerRequest: null }` é a forma correta e verificada de configurar a conexão sem este projeto assumir a API do `ioredis` além do que o único peer dependency exige.
- `maxRetriesPerRequest: null` é exigido para conexões de **Worker** (não apenas recomendado) — confirmado no guia oficial de conexões — porque um Worker mantém uma conexão bloqueante que precisa retentar indefinidamente em vez de desistir numa breve indisponibilidade do Redis.
- `BackoffOptions` (verificado em `node_modules/bullmq/dist/esm/interfaces/backoff-options.d.ts` e `classes/backoffs.js`) já tem um campo `jitter` nativo (fração 0–1) tanto para `fixed` quanto `exponential` — satisfaz "backoff exponencial + jitter" (seção J) sem precisar de uma `backoffStrategy` customizada.
- `UnrecoverableError` (importável de `"bullmq"`) força um job para o estado `failed` **imediatamente**, ignorando `attempts` restantes — verificado no código-fonte (`Job.shouldRetryJob`: a condição de retry é `attemptsMade + 1 < opts.attempts && !(err instanceof UnrecoverableError)`). É o mecanismo usado para separar "erro permanente" (não vale a pena gastar tentativas) de "erro transitório" (vale retentar).
- **Achado empírico, não documentado claramente em lugar nenhum**: o evento `'failed'` do Worker dispara em **toda** tentativa falha, não só na falha terminal — confirmado lendo `Worker.handleFailed`/`Job.moveToFailed`. O sinal correto para "esta foi a falha terminal" é `job.finishedOn` estar definido (só é setado no branch de `moveToFailed` que NÃO agenda retry) — verificado lendo o código-fonte linha a linha, não assumido. Sem essa verificação, um listener ingênuo gravaria uma entrada no Dead Letter a cada tentativa intermediária, mesmo em jobs que acabam tendo sucesso no retry seguinte.
- **Achado empírico sobre reuso de `jobId`** (testado diretamente contra um Redis real, não deduzido da documentação): reenfileirar um job cujo `jobId` já existe num estado terminal (completed/failed) é um no-op silencioso — o processor NUNCA roda de novo, mesmo que os dados passados sejam diferentes. Isso é uma restrição real que a Fase 12 (Reconciliation Engine) precisará respeitar para reprocessar um pedido que já passou pelo Dead Letter: remover o job antigo (`queue.remove(jobId)`) antes de reenfileirar — documentado no teste `metaWorker.test.ts` que demonstra exatamente esse padrão.
- Códigos de erro do Graph API classificados como transitório vs. permanente verificados contra `developers.facebook.com/docs/graph-api/guides/error-handling` (não inventados): transitório — 1 (API Unknown), 2 (API Service), 4/17 (rate limit), 341 (limite de aplicação), 368 (bloqueio temporário por política); permanente — 3 (API Method/permissão), 10 (permissão negada), 102/190 (sessão/token inválido ou expirado), faixa 200-299 (API Permission).

**Decisões de design:**
- **Separação clara entre "erro estrutural/de dado" e "erro real do Meta CAPI"**, no processor do worker (`lib/metaWorker.ts`): `consent_not_granted` e os quatro status de jornada não resolvida (`order_not_found`, `no_checkout_correlation`, `checkout_not_tracked`, `session_not_tracked`) **completam o job normalmente** (sem lançar exceção) — retentar em segundos não muda o consentimento salvo nem os dados do pedido no Shopify. `network_error` e `http_error` **lançam** uma exceção (para acionar o backoff/attempts do BullMQ), classificando `http_error` como permanente (`UnrecoverableError`, pula retries) ou retryable (`Error` comum, retenta) via `lib/metaErrorClassification.ts`. Um código de erro do Meta não reconhecido (fora dos dois conjuntos documentados) é tratado como retryable — escolha deliberadamente conservadora: retentar um erro permanente por engano só gasta algumas tentativas extras antes de cair no Dead Letter de qualquer forma; tratar um erro transitório real como permanente descartaria um Purchase recuperável.
- **Credenciais do Meta nunca fazem parte do payload do job** (`MetaCapiJobData` é só `{orderId, shopId}`) — são resolvidas de novo a partir do config no momento do processamento (`resolveMetaCredentials`), tanto porque o job payload fica persistido no Redis (não é o lugar certo para um segredo) quanto porque credenciais podem ser rotacionadas sem precisar re-enfileirar nada.
- **Falta de credenciais do Meta configuradas é tratada como erro permanente** (`UnrecoverableError("meta_not_configured")`) — não adianta retentar um job enquanto ninguém conectou uma conta Meta real; fica no Dead Letter até alguém notar e configurar, nunca descartado silenciosamente.
- **`dead_letters` é uma tabela própria no Postgres, não só o `failed` set do BullMQ em Redis** — porque a Fase 12 (Reconciliation Engine) já consulta Postgres para tudo (spec seção J), nunca Redis; um Dead Letter que só existisse em Redis seria invisível para ela. Único em `(queue_name, job_id)`: uma segunda falha do mesmo job lógico atualiza a linha existente (`failure_reason`/`attempts_made`/`last_failed_at`) em vez de duplicar — mesmo padrão de "nunca duplicar, sempre mesclar" já usado em `identity_private`.
- **Gravação no Dead Letter acontece em exatamente dois lugares, sem sobreposição**: dentro do processor (sem exceção) para os status estruturais/de dado; no listener `worker.on("failed", ...)` (usando o sinal `job.finishedOn`) para os erros reais do Meta CAPI — nunca os dois ao mesmo tempo para o mesmo job, evitando tanto duplicação quanto lacunas.
- **Enfileiramento no webhook `orders/paid` é best-effort, fail-open** (`routes/webhooks.ts`): se `REDIS_URL` não está configurado (`app.metaQueue` é `undefined`) ou o `queue.add()` falha, o webhook ainda responde 200 — nunca transforma um pedido já ingerido com sucesso numa falha de entrega do webhook Shopify (spec seção J: "fail-open comercial").
- **Worker roda como processo separado** (`src/worker.ts`, novos scripts `npm run worker` / `worker:start`), não como efeito colateral de `buildServer()` — corresponde ao "Queue + Workers" como componente lógico próprio (seção A do `ARCHITECTURE.md`), e já deixa o projeto no formato que a Fase 16 (deployment) vai precisar (worker como seu próprio serviço/container).
- **`createMetaCapiQueue`/`createMetaCapiWorker` aceitam um `prefix` opcional** (namespace de chaves Redis do BullMQ) — usado pelos próprios testes deste projeto para isolar as filas de cada arquivo de teste no mesmo Redis compartilhado; também útil em produção para rodar mais de um ambiente contra um único Redis.

## Correção de Arquitetura — Multi-Loja de Destino

**Não é uma nova fase numerada** — é uma correção a código já entregue nas Fases 3/4/5/7, motivada por uma descrição detalhada da topologia real de lojas feita pelo usuário, e tratada com o mesmo rigor (pesquisa → decisão → implementação → lint → typecheck → testes → documentação) de qualquer fase.

**O achado**: o design original (Fases 3/4/5/7) assumia exatamente duas lojas Shopify fixas — "Store A" (vitrine) e "Store B" (checkout único) — com `SHOPIFY_A_*`/`SHOPIFY_B_*` como variáveis de ambiente nomeadas e um domínio de destino hardcoded em `GET /r/:token`. O usuário descreveu a topologia real: UMA loja Hub (vitrine) com diversos produtos, cada um podendo redirecionar para uma de VÁRIAS lojas de destino distintas (2 a 10, cada uma sua própria loja Shopify/domínio/conta Shopify Payments) — a mesma página do Hub podendo enviar cliques de produtos diferentes para lojas de destino diferentes. O pedido explícito foi verificar se o rastreamento ponta-a-ponta funcionaria "cem por cento" com esse formato, sem perder dados, e confirmando que domínio muda por loja.

**Auditoria do código existente antes de qualquer mudança**: em vez de assumir que o problema era generalizado, o pipeline inteiro foi revisado achando exatamente três pontos hardcoded para duas lojas — e confirmando que o resto já generalizava para N lojas sem alteração:
- `shop_id` já era um campo texto livre em todo o schema/eventos/atribuição/Identity Graph/consentimento/Meta CAPI (nunca um enum restrito a "store-a"/"store-b") — nenhuma mudança necessária aí.
- A extensão Web Pixel já lê `shop_id` do seu próprio `settings` por instalação (`shopify.extension.toml`) — instalar o mesmo pixel em N lojas de destino já funciona sem nenhuma mudança de código no pixel, apenas N instalações + N configurações.
- Os três pontos genuinamente hardcoded: (1) `GET /r/:token` montava a URL de redirecionamento com um domínio único fixo do Gateway inteiro; (2) a tabela `transfers` não tinha nenhuma coluna de referência a qual loja de destino aquele transfer específico pertencia; (3) `/webhooks/:store/*` só reconhecia exatamente dois nomes de loja fixos, cada um com sua variável de segredo própria hardcoded (`SHOPIFY_A_WEBHOOK_SECRET`/`SHOPIFY_B_WEBHOOK_SECRET`).

**Perguntas feitas ao usuário antes de desenhar a correção** (para não superdimensionar nem assumir errado): (1) como o produto sabe para qual loja de destino ir — resposta: já existe no Shopify (tag/metafield/coleção), o tema só precisa ler e encaminhar; (2) quantas lojas de destino e com que estabilidade — resposta: poucas e estáveis (2 a 10). Essas duas respostas descartaram a alternativa de um cadastro dinâmico de lojas no banco (que ninguém pediu e adicionaria complexidade sem necessidade) em favor de um registro configurável por variável de ambiente.

**Pesquisa (verificação, não suposição)**: antes de desenhar a correção, verifiquei diretamente na documentação oficial do Shopify (shopify.dev, "Authenticate app proxies", via WebFetch/WebSearch) se `SHOPIFY_APP_PROXY_SECRET` precisaria virar um segredo por loja sob a nova topologia. Confirmado que não: a assinatura de uma requisição de App Proxy usa o client secret OAuth único do app instalado, o mesmo valor não importa de qual loja veio a requisição — nunca um segredo por instalação. Isso evitou introduzir um design incorreto (segredo de app proxy por loja) que a documentação não sustenta.

**Design da correção — registro `SHOPIFY_STORES` config-driven**:
- `apps/gateway/src/config.ts`: novo `storeEntrySchema` (`shop_id`, `domain`, `role: "storefront"|"checkout"`, `webhook_secret`) e `SHOPIFY_STORES` — uma variável de ambiente contendo um array JSON, parseada e validada via Zod (`parseStoresJson`, com detecção de `shop_id` duplicado). Removidas `SHOPIFY_A_SHOP_DOMAIN`/`SHOPIFY_B_SHOP_DOMAIN`/`SHOPIFY_A_WEBHOOK_SECRET`/`SHOPIFY_B_WEBHOOK_SECRET`. Nova função `findStoreByShopId(config, shopId)` — o único ponto de resolução `shop_id → loja`, usado por toda rota store-aware; retorna `undefined` para uma loja não registrada, e todo chamador falha fechado (nunca adivinha um destino).
- `packages/db/src/schema.ts` + migration `0004_left_devos.sql`: `transfers.destination_shop_id` (texto, `NOT NULL`) — persiste por transfer qual loja de destino aquele clique específico deve resolver, em vez de um destino único assumido para o Gateway inteiro.
- `lib/transferSchemas.ts`/`lib/transfer.ts`: `destination_shop_id` passa a ser obrigatório no corpo de `/transfer/create` e é propagado para `createTransfer()` → persistido → devolvido por `recordTransferRedirect()`.
- `routes/transfer.ts` (`GET /r/:token`): resolve `findStoreByShopId(app.config, outcome.destinationShopId)` e monta a URL de redirecionamento com o domínio DAQUELA loja de destino especificamente; se a loja não estiver mais registrada, responde 500 (`redirect_target_not_configured`) em vez de adivinhar.
- `routes/proxy.ts`: `/proxy/transfer/create` propaga o mesmo `destination_shop_id` do corpo da requisição.
- `routes/webhooks.ts`: `authorizeWebhook()` substitui a checagem de dois nomes fixos por `findStoreByShopId()` — uma loja não registrada responde 404 (`unknown_store`) antes mesmo de checar HMAC; uma loja registrada usa exclusivamente o `webhook_secret` daquela entrada, nunca um segredo compartilhado entre lojas.
- `extensions/checkout-bridge-store-a/src/checkoutBridge.ts`: `InitiateTransferOptions` ganha `destinationShopId`, incluído no corpo da requisição para `/transfer/create` — o elo final entre o clique no tema do Hub e a resolução correta no Gateway.
- `extensions/checkout-bridge-store-a/snippets/buy-on-store-b.liquid.example`: reescrito para ilustrar a leitura de `destination_shop_id` (e do domínio de fallback correspondente) a partir de metafield/tag do próprio produto, renderizado por-produto (não mais um botão único fixo para "Store B").
- `.env.example`: `SHOPIFY_STORES` com um exemplo de Hub + duas lojas de destino, substituindo as variáveis antigas.
- `docs/ARCHITECTURE.md` Seção C: reescrita ("Hub → Múltiplas Lojas de Destino — Identity Strategy") descrevendo a topologia real, o registro `SHOPIFY_STORES`, e como o Transfer Token agora carrega `destination_shop_id` por linha.

**Prova concreta de que a correção funciona (não apenas "compila")**: dois novos testes em `apps/gateway/src/server.test.ts` — um enviando dois transfers da MESMA sessão de rastreamento para `destination_shop_id` diferentes (`store-b` e `store-c`) e confirmando que cada um resolve para o domínio correto (`store-b.example.com` vs `store-c.example.com`) na mesma execução de teste; outro confirmando que um `destination_shop_id` não registrado falha fechado com 500 em vez de redirecionar para qualquer lugar. Em `apps/gateway/src/routes/webhooks.test.ts`, um novo teste registra uma TERCEIRA loja (`store-d`, deliberadamente distinta de `store-c`, que continua propositalmente não-registrada para exercitar o caminho "loja desconhecida") com seu próprio segredo de webhook e confirma que um webhook assinado com aquele segredo é aceito — prova direta de que o registro suporta N>2 lojas, não apenas as duas originais.

**Testes**: nenhum teste foi removido; os existentes foram adaptados para o novo formato de configuração (`SHOPIFY_STORES` no lugar de `SHOPIFY_A_WEBHOOK_SECRET`/`SHOPIFY_B_WEBHOOK_SECRET`/`SHOPIFY_B_SHOP_DOMAIN`, `destination_shop_id` adicionado a todo payload de `/transfer/create`) mais 5 novos (2 em `server.test.ts`, 2 em `webhooks.test.ts`, 1 em `checkoutBridge.test.ts` confirmando que `destination_shop_id` é enviado no corpo da requisição). Total no monorepo: **180/180 passando** (schema 9, db 6, pixel-kit 13, gateway 127, web-pixel-store-a 5, web-pixel-store-b 11, checkout-bridge-store-a 9). Lint, typecheck e build limpos em todos os pacotes.

**Pendências explícitas**: nenhuma — esta correção fecha completamente o gap identificado pelo usuário (Hub → N lojas de destino, cada uma seu próprio domínio, sem perda de dados de atribuição). A Fase 12 (Reconciliation Engine) segue como o próximo trabalho planejado, agora sobre uma base que já reflete corretamente a topologia real do merchant.

## Phase 12 — Reconciliation Engine

**Escopo (docs/ARCHITECTURE.md seção J, linha 278)**: comparar `orders(financial_status=paid)` × `event_registry(event_name=Purchase, meta_sent)` × respostas do Meta, gerando `MATCHED / MISSING_LOCAL / MISSING_META / DUPLICATED / VALUE_MISMATCH / CURRENCY_MISMATCH / UNATTRIBUTED`, nunca fabricando atribuição para fechar a conta.

**Limite de escopo documentado explicitamente (não escondido)**: esta engine compara Postgres contra Postgres. Ela NÃO consulta o lado do Meta ao vivo — o Meta não expõe uma API de consulta para "quais eventos CAPI eu de fato recebi/casei por event_id" (Events Manager é uma UI; as APIs de Insights/match-rate reportam métricas agregadas de qualidade, não uma busca por evento individual). "Respostas do Meta" aqui significa o registro durável que este próprio Gateway já mantém do que o endpoint `/events` do Meta respondeu no momento do envio (`meta_deliveries`) — o único sinal honestamente disponível, nunca uma checagem inventada contra uma API que não existe para esse propósito.

**Decisão de design — nova coluna em vez de recomputar**: para detectar `VALUE_MISMATCH`/`CURRENCY_MISMATCH` de forma honesta (sem re-derivar `orders` no momento da leitura, o que compararia o pedido contra si mesmo), `meta_deliveries` ganhou duas colunas novas — `value_sent`/`currency_sent` — um snapshot exato do que aquele envio específico realmente disse ao Meta, capturado em `sendPurchaseToMeta()` no momento do envio. A comparação na reconciliação é sempre "o que foi enviado" vs. "o que `orders` diz agora", nunca as duas lidas do mesmo lugar.

**Categorização (`lib/reconciliation.ts`)**:
- `event_registry.meta_sent = true` → **MATCHED** (ou **DUPLICATED** se houver mais de uma linha `delivered` em `meta_deliveries` para o mesmo `event_id` — nunca deveria acontecer dado o gate de dedup em `sendPurchaseToMeta`, mas é exatamente o tipo de bug que esta engine existe para revelar; ou **VALUE_MISMATCH**/**CURRENCY_MISMATCH** se o snapshot da última entrega divergir do `orders` atual). Uma linha `dead_letters` remanescente de uma falha anterior é limpa automaticamente aqui — o pedido já se recuperou.
- Sem entrega bem-sucedida, mas com uma linha em `dead_letters`: o `failure_reason` decide **UNATTRIBUTED** (um dos gaps estruturais que `lib/metaWorker.ts` já grava diretamente — `consent_not_granted`, `order_not_found`, `no_checkout_correlation`, `checkout_not_tracked`, `session_not_tracked` — nunca sequer chegou a tentar o Meta) vs. **MISSING_META** (um erro real do Meta CAPI, permanente ou com tentativas esgotadas).
- Sem entrega e sem dead letter: ainda legitimamente em trânsito, A MENOS que o pedido tenha sido pago há mais de `RECONCILIATION_STALE_AFTER_MINUTES` (default 15) — só então é **MISSING_META** (`no_delivery_attempt_recorded`), cobrindo o caso real de "caiu pelas rachaduras" (ex.: `REDIS_URL` fora do ar no momento exato do `orders/paid`, cujo enfileiramento é fail-open por design — Fase 11).
- **MISSING_LOCAL** (a direção reversa, que `scanPaidOrders` nunca poderia encontrar sozinho pois parte de `orders`): uma linha `event_registry` com `event_name='Purchase' AND meta_sent=true` cujo `order_id` (extraído do `event_id` `purchase:{shop_id}:{order_id}`) não existe mais (ou nunca existiu) em `orders` — um gap de integridade local genuíno.

**Remediação automática, deliberadamente separada da varredura (`requeueEligibleOrders`)**: `runReconciliation()` é puramente leitura (nenhum efeito colateral em fila), então é seguro chamá-la de qualquer contexto somente-leitura (o dashboard da Fase 13 incluído) sem risco de um reenfileiramento em massa por acidente. O reenfileiramento de verdade só acontece em `requeueEligibleOrders()`, e só para `MISSING_META`/`UNATTRIBUTED` (reenviar um `MATCHED`/`DUPLICATED` só pioraria a duplicação; um `*_MISMATCH` precisa de decisão humana, não de um retry). Respeita diretamente a restrição documentada na Fase 11 ("reenfileirar um job cujo `jobId` já existe num estado terminal é um no-op silencioso"): remove o job antigo (`queue.remove(jobId)`) antes de reenfileirar. Limitado em dois eixos configuráveis — `RECONCILIATION_MAX_REQUEUE_ATTEMPTS` (nunca mais que N tentativas por pedido — um pedido permanentemente quebrado deve eventualmente aparecer para um humano, não ser retentado para sempre) e `RECONCILIATION_REQUEUE_COOLDOWN_MINUTES` (nunca antes de N minutos desde a última falha — evita martelar o Meta/a fila a cada ciclo do cron).

**Processo próprio, não efeito colateral**: `src/reconciliationCron.ts` é um processo standalone (`npm run reconciliation` / `reconciliation:start`), mesmo padrão do worker da Fase 11 — "Reconciliation Engine (job periódico)" é seu próprio componente lógico (docs/ARCHITECTURE.md seção A), nunca algo que o Gateway HTTP ou o worker do Meta CAPI rodam de brinde. Funciona mesmo SEM `REDIS_URL` configurado (diferente do worker) — uma varredura somente-leitura ainda é um sinal valioso (grava linhas em `reconciliation_runs`) mesmo quando enfileiramento não está disponível; `scheduleReconciliation()` detecta a ausência da fila e apenas registra e pula o reenfileiramento, nunca lança. Agendamento via `node-cron@4.6.0` — verificado diretamente no `.d.ts` do pacote instalado (`schedule()` retorna um `ScheduledTask` cujo `.stop()` é o que um desligamento gracioso precisa, não um handle de intervalo cru).

## Phase 15 — Revisão de Segurança

**Escopo**: revisão do código entregue nas Fases 0-14 contra o checklist de segurança do spec (seções 41-45/63: segredos nunca no browser/payload de fila, HMAC em toda superfície privilegiada, consentimento antes de qualquer envio ao Meta, PII minimizada/isolada, auditoria sem PII). Documento completo em `docs/SECURITY_REVIEW.md` — esta entrada resume achados e resultado; ver aquele arquivo para o detalhamento de cada item.

**Achados corrigidos**:
1. **Vazamento potencial do access token do Meta em mensagem de erro de rede.** `lib/metaCapiClient.ts`'s `sendMetaCapiEvent()` monta a URL do Meta CAPI com `access_token` como query param (única forma documentada de autenticar essa API). Se `fetch()` falhar por erro de rede, algumas implementações embutem a URL completa da requisição na mensagem/causa do erro — que seria então persistida em `dead_letters.failure_reason` (Postgres, Fase 11) e poderia chegar a logs. Nunca observado a ocorrer neste projeto, mas corrigido como defesa em profundidade: a mensagem de erro agora tem o `access_token` removido (`[REDACTED]`) antes de retornar, sempre. Novo teste em `metaCapiClient.test.ts` simulando exatamente esse cenário.
2. **`drizzle-orm` — CVE de SQL injection via identificadores mal escapados** (GHSA-gpj5-g38j-94v9, `npm audit`, high). Auditado todo uso de `sql\`...\`` no projeto (dois locais, `lib/eventRegistry.ts`/`lib/identity.ts`) — nenhum interpola uma string dinâmica como identificador (sempre um `Column` do schema ou um valor tipado/validado), então nenhum caminho de código é explorável hoje. Ainda assim, corrigido por ser uma atualização sem breaking change observável: `drizzle-orm` `^0.36.4` → `^0.45.2`, `drizzle-kit` `^0.28.1` → `^0.31.10`. Verificado: build limpo, `drizzle-kit generate` reporta zero drift de schema, suite completa re-executada sem regressão.

**Achados revisados e aceitos sem mudança de código**: as 8 vulnerabilidades restantes do `npm audit` traçam inteiramente a ferramental de desenvolvimento (`esbuild`/`vite`/`vitest`, nunca presentes no artefato de produção compilado); os três mecanismos de HMAC (`crypto.ts`, `shopifyWebhookAuth.ts`, `appProxy.ts`) já usavam `timingSafeEqual` com checagem de comprimento e captura de erro de decodificação; o gate de consentimento em `sendPurchaseToMeta()` e o isolamento de PII em `identity_private` (apenas hashes, os campos `*_enc` reservados nunca escritos) já estavam corretos; o Admin Dashboard (Fase 13) já falha fechado e nunca compara senha em texto puro — HTTPS em produção é um requisito operacional documentado para a Fase 16, não uma correção de código.

**Riscos residuais aceitos / recomendações operacionais para a Fase 16**: `trustProxy: true` do Fastify exige que o proxy reverso real de produção sobrescreva (nunca repasse) `X-Forwarded-For` de clientes; o token de transferência cross-domain viaja como query param no `Location` de um redirect 302 (mitigado por TTL curto, resgate atômico de uso único, e detecção de replay já auditada — risco inerente a qualquer esquema bearer-token-em-URL, recomendação é tratar logs de acesso como sensíveis); o rate-limit único e global (100 req/min) idealmente seria calibrado por rota antes de produção em escala, mas não há perfil de tráfego real ainda para calibrar contra.

**Já adequado por padrão, sem ação**: limite de payload (1MB, Fastify default), CORS fail-closed, Helmet com defaults, ausência de `setErrorHandler` customizado (nunca vaza stack trace), redação de log já cobrindo `authorization`/`x-gateway-signature` (incluindo as novas credenciais do Admin Dashboard).

**Resultado final**: após as duas correções, suite completa re-executada em todos os 7 workspaces — lint, typecheck e testes limpos. **219/219 testes passando** no monorepo inteiro: schema 9, db 6, pixel-kit 13, gateway 166, web-pixel-store-a 5, web-pixel-store-b 11, checkout-bridge-store-a 9 (o incremento de 218→219 é exatamente o novo teste de redação do access token). Nenhuma regressão introduzida pelas correções desta fase.
